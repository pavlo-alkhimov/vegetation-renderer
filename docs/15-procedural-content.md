# 15 — Procedural content system: recipes instead of data

State: October 2026. Decision: content is described by **recipes** — graphs of generator operators with parameters
and seeds — and generated by our own code, in the spirit of Farbrausch's .werkkzeug and .kkrieger. Goals:

1. no or almost no input resources: the repository holds code and a few kilobytes of recipe text per asset;
2. full artistic control: every visible property is a parameter with a live preview, not a property of some
   downloaded data.

Real-world data stays in the project in two roles only (option b + c): as an **optional import operator** and as
**statistics** that become recipe parameters and validation targets. Priority: plants first ([14](14-procedural-plants.md));
textures, meshes, terrain and placement use the same system later.

## 1. Precedent: .kkrieger and .werkkzeug

.kkrieger (Farbrausch, 2004) is a first-person shooter in 96 KB: textures, meshes, materials and animation are stored
as their creation history and generated at start-up. The group released its tools in 2012
([`farbrausch/fr_public`](https://github.com/farbrausch/fr_public)): `werkkzeug3` and its `werkkzeug3_kkrieger` branch
(BSD-2), Werkkzeug4 in `altona_wz4` (BSD, the most complete), `ktg` / OpenKTG (texture generator, public domain).

What the source shows:

| Element | In the code |
|---|---|
| Bitmap operators (`genbitmap.cpp`) | Perlin, Cell, Gradient, Bricks, Dots, GlowRect, Blur, Sharpen, Normals, Bump, Light, Distort, Twirl, Rotate, Merge, Mask, HSCB, ColorBalance, Range, Text, Render |
| Mesh operators (`genmesh.cpp`, `genminmesh.cpp`) | primitives (Cube, Cylinder, Sphere, Torus, Grid), Extrude, ExtrudeNormal, Subdivide, Bevel, Bend, Displace, Perlin, Crease, UVProjection, Transform, Multiply (instancing), selections (Cube, Sphere, Angle, Random, Grow, Logic) that restrict the next operators, BoneChain, Pipe |
| Operator declaration (Werkkzeug4 `.ops` files, ~310 operators) | one block per operator: typed inputs with defaults, parameters with type, range, step, enum labels and default, and the code; the tool derives UI, file format, value clamping and caching from it |
| Texture core (`ktg/gentexture.*`, ~1.4 k lines) | 16-bit RGBA pixels, noise (white / band-limited, octaves, abs), cells (inner/outer distance), gradients, colour matrix, coordinate remap, derive (normals), blur, ternary/combine ops, paste, bump lighting |

Why it gave artists control: every operator's output can be previewed, parameters have sensible ranges, and complex
looks are built from many small decisions (a few dozen operators per texture). Randomness is always a seed parameter,
so "a different one" is a click, and "this one" is reproducible.

Comparable tools today: Houdini (the industry form of the idea), Substance Designer, Blender Geometry Nodes, Material
Maker, Tooll3 (MIT). None is used here: the recipes must run inside our own cooker and viewer.

## 2. Principles

| Principle | Consequence |
|---|---|
| Recipe, not data | assets are text files in `assets/recipes/`; generated results live in `data/cooked/` and a cache, both git-ignored and rebuilt on any machine |
| One declaration per operator | an X-macro table in C (name, type, range, default, enum labels per parameter) yields the parameter struct, the recipe parser, clamping, defaults, the hash, the viewer's parameter panel and the `--ops` documentation; no code generator |
| Determinism | same recipe + same code → same result; every random choice comes from a seed parameter; derived seeds are `hash(seed, node name)`, so adding a node does not reshuffle the others |
| Content-hash caching | result key = hash(operator, parameters, input keys); changing one parameter regenerates only the dependent nodes |
| Live preview | the viewer hot-reloads recipes and shows any node's output in the gallery |
| Small hand-made input | where control by parameters is not enough: vector overrides inside the recipe (points, polylines, polygons, strokes), kilobytes, never bitmaps |
| Real data = import + statistics | `Import*` operators are optional; `Measure*` operators turn real data into a few numbers committed as parameters and targets |

## 3. Model

**Types** flowing along graph edges: `Bitmap` (RGBA16, ktg pixel), `Field` (one-channel float grid: heights, masks,
densities), `Mesh` (indexed triangles + attributes + selection), `Skeleton` (plant axes: nodes, orders, radii, buds),
`Organ` (leaf, needle, flower shape + mesh), `Plant` (skeleton + organs + materials → LODs), `PointSet` (placements),
`Params` (a named parameter block, reusable), `Stats` (measured numbers).

**Operators:** inputs (typed, optional with defaults), parameters, one C function. Declaration sketch:

```c
#define PARAMS_Perlin(P) \
    P(INT,   size,    16, 4096, 512) \
    P(INT,   freq,     1,   64,   4) \
    P(INT,   octaves,  1,   12,   5) \
    P(FLOAT, falloff,  0,    1, 0.5) \
    P(ENUM,  mode,     "direct|abs|sin", 0) \
    P(SEED,  seed,     0,    0,   0)
OPERATOR(Perlin, BITMAP, INPUTS_NONE, PARAMS_Perlin, "band-limited noise, ktg Noise")
```

**Recipe text format** — one node per line, references by name, order-free, comments, includes; line-oriented so git
diffs stay readable:

```
# assets/recipes/beech.recipe
include "plants_common.recipe"
growth   = GrowthParams  apical=0.55 tropism_up=0.30 shed=0.12 internode=0.035 branch_angle=42 phyllotaxis=distichous
tree     = GrowBroadleaf params=growth habitat=forest age=80 plot=5 seed=1
leaf     = LeafShape     outline=ovate length=0.075 width=0.045 margin=wavy teeth=7 veins=7 seed=5
leaf_mat = LeafMaterial  shape=leaf chlorophyll=45 carotenoids=9 anthocyanins=0.5 brown=0 structure=1.6
bark_n   = Perlin        size=1024 freq=6 octaves=6 falloff=0.55 seed=12
bark_c   = Cells         size=1024 count=160 mode=outer seed=3
bark     = BarkSmooth    noise=bark_n cells=bark_c lenticels=0.35 scars=0.6 color0=#8b8c87 color1=#5c5d59
out      = PlantAsset    tree=tree leaf=leaf leaf_material=leaf_mat bark=bark lods=4 variants=6
```

**Sub-recipes** (Werkkzeug's macro operators): a recipe file with declared parameters is an operator itself
(`BarkSmooth` can be a sub-recipe of Perlin, Cells, Blur, Normals and colour ops instead of C code). Artists extend
the operator set without touching C; C operators exist where speed or algorithms require them (growth, venation,
PROSPECT-D, erosion).

**Evaluation:** parse → resolve names → topological order → per node: key = hash; cache hit (memory, then
`data/cache/<key>.bin`) or execute. Independent nodes run in parallel; results never depend on thread scheduling.

**Variants:** `variants=N` on an output node evaluates the graph N times with derived seeds; parameter sweeps
(`age=40..120 step 40`) produce galleries for comparison.

## 4. Operator families

| Family | Operators (first set) | Priority |
|---|---|---|
| Plant structure | `GrowthParams`, `GrowBroadleaf` (self-organising growth), `GrowConifer` (whorl rules), `LSystem` (herbs), `Prune`, `Bend` | **first** ([14](14-procedural-plants.md)) |
| Plant organs | `LeafShape` (outline, margin, venation), `Needle`, `NeedleSpray`, `Flower`, `Blade` | **first** |
| Plant materials | `LeafMaterial` (venation maps + PROSPECT-D), `BarkSmooth`, `BarkFurrowed` (fracture strips), `BarkPlated`, `SeasonRamp` | **first** |
| Plant assets | `PlantAsset` (LOD build, meshlets, card/billboard bakes, `.vpl` output) | **first** |
| Bitmap (ktg port) | `Noise`, `Cells`, `Gradient`, `Flat`, `Blur`, `Normals` (derive), `Combine`, `ColorRemap`, `CoordRemap`, `ColorMatrix`, `Paste`, `Bump`, `Range` | first (needed by the materials) |
| Mesh (werkkzeug-style) | primitives, `Extrude`, `Subdivide`, `Bevel`, `Bend`, `Displace`, `Multiply`, `Select*`, `UVProject` | later: rocks, deadwood, props, buildings |
| Terrain | `ImportDGM1` (optional), `TerrainNoise`, `Erosion` (hydraulic, thermal), `Terrace`, `River` | later |
| Placement | `Slope`, `Altitude`, `Wetness`, `Exposure` masks, `Combine`, `Density`, `Scatter` (with species rules) | later |
| Statistics (option c) | `MeasureTerrain` (height spectrum, slope histogram, drainage density), `MeasureForest` (patch sizes, edge length, canopy height distribution), `MeasureTrees` (allometry, QSM statistics) | with each family |

## 5. Real data under b + c

| Data | Role |
|---|---|
| DGM1 terrain (1 GB download) | `ImportDGM1` stays available as one terrain source; `MeasureTerrain` extracts statistics (roughness spectrum, slope and curvature histograms, valley density) committed as a small parameter file; procedural terrain is validated against them |
| Land cover, forest stands, canopy heights ([13](13-reference-maps.md)) | statistics for placement rules (patch sizes, edge shapes, species mixtures by altitude and slope); optional import for a "real place" mode |
| Tree scans, allometry | targets for the plant generators ([14](14-procedural-plants.md) §4) |
| Poly Haven ground-cover scans ([06](06-vegetation.md) §5.14) | interim; replaced by generated herbs and grasses; kept as visual reference |
| Photographs | look-dev targets only |

Only derived numbers (and their source and licence) are committed.

## 6. Tools and editing

| Phase | Editing | Preview |
|---|---|---|
| 1 | recipes in any text editor | `vr --recipe <file>` hot-reloads on save; gallery shows the selected node's output (bitmap, mesh, plant); console prints node timings and cache hits |
| 2 | parameter panel in the viewer: select node, change values with keys/mouse, written back into the recipe text (comments and layout kept) | live |
| 3 | graph view (Werkkzeug-like stacked operators) | live |

Batch: `vrgen <recipes...>` produces the cooked files (same code as the viewer's preview). `vrgen --ops` prints the
operator reference generated from the X-macro table.

## 7. Size and time

- Recipes: a plant species ~2–10 KB, a texture ~1–3 KB; the whole biome stays well under 1 MB of text.
- Generation: textures milliseconds to a second; a grown tree seconds; done once per change thanks to the cache.
  Cooked output (meshlets, textures) is large but never committed.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Text recipes are slower to art-direct than painting | live preview from day one; parameter panel (phase 2); vector overrides for the cases parameters cannot reach |
| Operator sprawl | sub-recipes for anything expressible by existing operators; C operators only for algorithms |
| Cross-platform float differences break bitwise determinism | determinism guaranteed per platform and compiler; cross-platform results compared with tolerances; no fast-math |
| Long generation stalls the viewer | evaluation on worker threads, previous result shown until the new one is ready |
| Procedural realism is not reached | option c: every family has measured targets from real data; galleries compare generated and reference side by side |
